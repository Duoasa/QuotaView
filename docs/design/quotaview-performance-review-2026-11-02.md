# QuotaView Mac 性能报告复核（2026-11-02）

更新：用户随后授权优化有价值的项目，首批 C3、E4、U3 及 C2 的共享首行缓存已实施于 0.9.1 Build 14。下文 33 项表格保留 Build 13 时的复核结论；实施与基准见文末。

原报告为用户提供的《QuotaView-Mac-性能排查报告.md》，基于 `main@1d10b40`。本次对照已合并的 `0a20049`（0.9.1 Build 12），另按用户要求实施 Build 13 的完成卡片中性背景；该颜色修改不属于下列性能优化。报告中的分工和修复步骤仅作为审查材料，没有据此启动子代理或实施整批优化。

结论：报告有价值，指出了多处可确认的重复工作，但只能作为优化候选清单。不能把它的 CPU、耗时、内存和系统调用估算作为当前应用的实测结论，也不能直接采用其中所有修复建议。最值得优先处理的是 rollout 不变文件的重复验证、候选发现重复工作、Claude 主线程 transcript 解码，以及圆球初始化时编译未使用的粒子渲染器。

## 已获取的证据与边界

- 核对了报告列出的 C1–C11、E1–E13、U1–U9 对应源码、调用条件及当前缓存/去重逻辑。
- 对本机默认 Codex 数据目录只读执行 `EXPLAIN QUERY PLAN`；未执行日志正文查询、写索引或修改数据库。当前 `logs_2.sqlite` 约 88.2 MiB、`state_5.sqlite` 约 35.0 MiB；大小仅为本机此时快照。
- 指定会话的执行元数据查询命中 `idx_logs_thread_id_ts (thread_id, ts)`；发现查询命中 `idx_logs_ts (ts)`。BLOB/LIKE 仍需过滤候选，但不能称为每次必然全库扫描。
- 会话列表查询命中 `idx_threads_archived`，并出现 `USE TEMP B-TREE FOR ORDER BY`。因此 C11 的额外排序有本机查询计划证据；不要修改 Codex 自己管理的数据库索引来规避应用侧工作。
- 查询计划原始记录：`.build/performance-review-091b13/query-plans.json`。没有进行 CPU/GPU profiling、冷启动计时或 5 分钟空闲/流式基准，不能量化节省收益。当前运行中的聊天活动也不能作为纯空闲样本。

| 编号 | 复核判断 | 当前事实与处理建议 |
| --- | --- | --- |
| C1 | 重复工作成立，严重程度待测 | `CodexLocalRolloutActivityClient.pollOnce` 默认每秒调用 metadata service；每次只读开库并 prepare，有 50ms VM 时间预算、分页游标与记录上限。本机查询命中索引，不能据此确认固定占用 5% CPU。先测查询耗时/预算命中，再做状态感知退避；必须保持内部任务识别及时性。数据库 mtime 单独不足以判定 WAL 是否变化。 |
| C2 | 成立，建议需调整 | `CodexLocalRolloutDiscovery` 对最多 1024 个数据库条目做身份/路径工作，目录发现还有逐批遍历、重新校验和排序取属性。缓存身份与文件属性有价值。但 1024 条也负责内部任务排除，不能简单先截 24 条，否则会破坏禁显/分类。系统调用量需采样，URL 属性读取不等同每次真实 stat。 |
| C3 | 成立，建议需调整 | 每 0.25s 的 consume 在 size 早退前验证路径、读取 session_meta；24 个候选时可发生最多约 96 次首行检查/秒。可以缓存首行/身份，但不能把整个早退移到所有逻辑之前：无文件增长时仍可能有数据库标题、子任务分类和恢复轮次变化需要发布。1–3MB/s 是估算，不是测量。 |
| C4 | 成立，条件性开销 | bootstrap 单候选上限 16MiB，并存在 decoder/public projection/metadata 重解析；24 个大文件可累计读 384MiB，但这不是已测启动耗时或峰值驻留内存。该 actor 也不是 MainActor。宜增量寻找当前轮次边界并共享解码结果，保持取消和重放恢复语义。 |
| C5 | 部分成立 | scan 枚举最多 2 万文件并重建去重汇总，确有随历史增长的工作；文件内容已有 offset/size/mtime 增量读取，删除文件也会清出 files，不是每次重读全部 jsonl 或所有 entries 永久不删。单个保留文件的 entry 累积仍值得改为增量日汇总。100万条/200MB 未验证。 |
| C6 | 成立 | `ClaudeCodeTranscriptDecoder` 即使用于 usage 扫描也构造文本/工具记录，timestamp 每次创建 formatter；`localDay` 每条创建 UTC Calendar。适合 usage 专用解析与隔离复用 formatter/calendar，避免跨线程共享可变解析器。具体秒数待测。 |
| C7 | 部分成立 | 入口 JSONSerialization 后还可能进入事件/Token decoder 和 public projection。分支受 handler 与会话类型控制，并非所有消息固定解析 3–4 次；建议传递一次解析的对象，保留隐私白名单和生命周期准入顺序。 |
| C8 | 成立 | shared app-server 默认每 0.5s 拉 loaded list，分页最多 10 页；订阅有去重。可按活跃状态退避，但先确认通知覆盖新线程发现、重连和漏事件，不能只把默认间隔放大后宣称无行为变化。 |
| C9 | 部分成立 | 独立用途可能拥有独立 app-server；必需请求失败/刷新替换等路径会 stop。但 optional usage 错误已吞掉，thread list 某类服务端错误有兼容重试，“任何请求失败都重启”不准确。复用必须按数据目录、环境、代理和账户隔离，不宜全局单进程。 |
| C10 | 实现成立，收益待测 | SHA256 后逐字节 `String(format:)` 存在。查表转十六进制是低风险候选；每秒几十毫秒没有证据。缓存需有容量上限，不能永久积累 thread ID。 |
| C11 | 成立，有查询计划证据 | 每轮开 state 库、读取表结构、查询最多 1024 条。本机 ORDER BY 使用临时 B-tree；可缓存 schema 和发现结果。不能仅依赖数据库主文件 mtime，也不能直接丢弃 C2 的内部任务排除范围。 |

## Hook 与系统集成

| 编号 | 复核判断 | 当前事实与处理建议 |
| --- | --- | --- |
| E1 | 成立，替代方案未证实 | Gemini BeforeModel 会启动 helper，输入先读完整有界 JSON，当前模型补充依赖此事件。直接移除会削弱模型识别；BeforeAgent/AfterAgent 是否提供可靠模型须核验。优先去重/缓存，并保留切模型更新。 |
| E2 | 阻塞存在，不接受直接只在 disposed flush | OpenCode finish 的 spawnSync 上限 1.5s；重发 in-flight 是有意的保交付设计，epoch/sequence 会去重。既有真实客户端测试发现 event dispatcher 不等待插件即退出，删除终态 flush 可能重现完成事件丢失。优化应保留退出前交付保证。 |
| E3 | 成立，不能无条件提前 ACK | Codex ACK 等待 MainActor 的准入、连接证据和处理结果。可拆出快速准入/可靠入队后再异步更新 UI；未接收成功就 ACK 会让 helper 不再走持久队列，并破坏安装期间重试语义。 |
| E4 | 成立，优先级较高 | Claude runtime 为 MainActor；活跃会话 1s tailTimer 和事件 drain 同步读取最多 2MiB，并生成完整记录。应后台读取/解码，携带会话与轮次 generation 回主线程提交；停用、截断、切轮时丢弃旧结果。计时器只在活跃且有 transcript 时开启。 |
| E5 | 部分成立 | Codex 启停/设置刷新可能再次 reconcile，检查有子进程和轮询；但 inspect/install 主体已在 Task.detached，且有 hookOperation 互斥，不宜统称主线程跑满 8s。可缓存环境检查和合并触发，保留数据目录/版本/信任变化失效条件。 |
| E6 | 部分已改善 | NativeAgent helper/route 仍会重写；外部 JSON 配置已有 original/result 相等早退。当前 Claude helper 已做字节比较，settings 也有语义比较，不是所有 provider 无条件重写全部文件。 |
| E7 | 成立，但不是普通事件直接阻塞 agent | OpenCode assistant message.updated 会重复 emit Metadata，两插件发送时都会重读 route。普通投递经后台异步队列；超时主要造成积压，真正同步阻塞见 E2。可去重 Metadata，route 缓存必须能检测更换、权限和认证变化。 |
| E8 | 成立 | statusLine 的 record 在原命令 forward 前同步通知并等 ACK，预算 0.15+0.25+0.25s。快照文件是持久来源，可缩短旁路等待；优化仍需保留用户原 statusLine 输出和超时清理。 |
| E9 | 成立，耗时待测 | 成功路径诊断存在文件锁、写入及临时 ISO8601 formatter。可采样或批写；失败/丢投递诊断应保留。低优先级，不能据源码断言微秒或亚毫秒量级。 |
| E10 | 成立 | 每条文件投递 ACK 后重新 drain/readdir/sort；积压批量完成时重复扫描值得合并。必须保持认证、in-flight 去重、时间顺序和失败重试。 |
| E11 | 部分成立 | Codex socket 每个读到的片段尝试解码；若 envelope 分片可多次解析，完整一次到达则不固定为 3 次。其他转换也有重复编码。等待完整有界帧再解码、减少结构往返合理，保留超时与过大输入拒绝。 |
| E12 | 成立，低频场景 | 若干 inspector/锁轮询仍 Thread.sleep，占用执行线程；部分新逻辑已采用有界非阻塞锁或 posix_spawn/poll。可以改异步等待，但不能把已有有界轮询都描述成 UI 阻塞或无限等待。 |
| E13 | 范围需缩小 | Application Support 的兼容客户端发现主要是 DSH；外部 Hook provider 在这之前已分流，并非每个 agent configure 都全目录扫描。缓存需允许用户新装客户端/增加配置目录后刷新。 |

报告列出的 Hook 超时是各阶段配置预算之和，并非正常调用实测延迟；文件 I/O、日志锁、进程启动等也不由该网络预算完整覆盖，因此不能称为严格端到端最坏上限。

## 后续建议与本轮实际改动

1. 先用同一版本、固定会话集合建立空闲/流式基准，记录 CPU 时间、文件读取次数、主线程长任务、Hook 延迟、丢事件率及 GPU 开销；当前只读计划不能替代基准。
2. 优先做 C3/C2 的缓存与重复验证收敛、E4 后台解码、U3 懒加载；随后根据基准决定 C1/C11 的查询缓存与退避、C6 的解析复用。
3. 再做 U1/U2 的发布粒度与布局索引，以及 E3/E8 的 ACK/状态栏路径优化。每步保留恢复、分类、退出交付、禁用和待确认语义。
4. 其余低优先级项目按实测热点安排，不把“轮询更慢”“先 ACK”“删 Hook”作为默认修复。

复核阶段仅实施用户另行要求的完成卡片取消背景染色：普通/hover、选中/未选中以及实体回退均为中性色，更新既有配色冒烟契约，3 项通过。该阶段开发包为 **0.9.1 Build 13 / 内部 146**，257 生产输入/19 资源与运行包核对通过。当时性能项尚未实施；以下为随后获得授权的优化批次。

## 首批性能优化（2026-11-02，0.9.1 Build 14）

- **C3 / C2 的重复首行读取**：发现与增量消费共用 actor 内的有界缓存，最多 2048 条；以实时 device、inode、size、纳秒级 mtime/ctime 判定是否变化。替换、同长改写、追加、截断、删除、权限变化会失效；不缓存不完整元数据，读取期间文件变化也不存入缓存。停止/换目录清理缓存。每次仍验证允许路径，仍处理无追加时的数据库标题、内部任务分类和精确轮次恢复；未缩小内部任务排除范围或降低轮询频率。
- **E4 Claude 主线程解析**：最多 2 MiB 的增量读取/JSON 解码及标题头部读取转到 utility 后台任务。Hook、轮询、helper 断开保持原接收顺序，积压的周期轮询合并；主线程只提交结果。运行代次、当前轮次与路径校验拒绝停止/重启后的旧结果；停用偏好立即阻止提交。保留 Stop 前排空、最新真实提问后的回放和 Token 去重，不调整 Hook 应答协议。
- **U3 圆球渲染器**：rippleGlow 可用时仅创建其渲染器；用户选择 particleOrb 或 rippleGlow 不可用才创建粒子回退，后续切换复用已创建的 view。状态、布局、Reduce Motion、停播不会意外初始化未使用渲染器。未改变视觉参数或窗口尺寸。

31 项针对性检查、0 失败、0 跳过。覆盖缓存失效、内部任务排除、只读权限/外链路径、原子替换、重入轮询、长会话/无追加恢复，以及 Claude 公开投影、停止后尾部结果、Hook 切轮顺序、禁用/重启、在途后台结果淘汰和渲染器复用。没有执行完整回归或 UI 自动验收。
