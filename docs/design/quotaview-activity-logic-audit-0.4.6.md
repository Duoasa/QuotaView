# QuotaView 0.4.6 灵动岛逻辑审计

日期：2026-09-05。状态：已按审计重构，自动验证和实机数据链路通过；本轮真实五步视觉已获用户确认，准备发布。

## 结论与边界

当前实现没有贯穿采集、状态存储和渲染的统一任务身份约束。它把“最近收到的
活动事件”近似当成“当前用户任务”，再把该事件投影到唯一灵动岛。内部审核
任务只是最先暴露问题的输入，单独排除一个来源不能解决状态串扰。

审计覆盖本地任务流、共享 App Server、Hook/队列入口，事件解码与接纳，
session/turn 状态，计划与 Token 聚合，启动恢复，完成/等待/收起以及渲染绑定。
额度面板和 Widget 的完整业务逻辑、第三方 Sparkle 内部实现不在本轮审计结论
范围；完成回执中的额度仅核对其与任务状态的连接边界。

审计基于提交 `4980fc5` 的生产源码、运行日志与针对性测试。最初新增的
guardian 局部过滤方案已撤回，未提交。没有把这次审计变成未经验证的重构。

## 从业务事实推导约束

1. **用户任务与系统执行单元不同。** 内部审核、子代理、工具调用可以各自完成，
   但它们的完成不能推导出用户任务完成。采集成功也不代表有权更新灵动岛。
2. **任务身份必须明确。** 运行状态属于 `(session, turn)`。来源、送达通道、
   到达时间和窗口标题均不能替代这个身份。
3. **当前展示归属与后台状态更新必须分开。** 其他任务可以更新自身状态，
   但一个后台 Stop 或 SessionEnd 不能夺取当前展示或改变它的动画生命周期。
4. **完成必须有正面证据。** 只有当前任务的可信成功终态能触发任务完成。
   Goal 完成、计划全完成、工具结束、无消息和缺失 turn ID 都不是同等证据。
5. **重放不能改变含义。** 相同开始事件不能清空已有进度；重启恢复与持续运行
   对同一段完整日志必须得到相同 Token 结果；终态不能被迟到状态复活。
6. **动画服从任务身份。** 同一任务内可以平滑、单调推进；切换任务必须能重置，
   不应通过延迟、忽略动画或百分比钳制掩盖状态错误。

## 静态审查确认的结构缺口

### 跨来源接纳并未统一

计划数据有明确来源优先级（localRollout > appServer > legacy），但生命周期
事件没有等价的准入层。Hook 在发送时生成时间，App Server 缺少 emittedAt 时
使用接收时间；因此，较新的时间不等于较新的任务事实。

共享客户端在 `CodexSharedAppServerActivityClient.swift:348` 枚举已加载线程，
在 `:378` 对所有线程调用 resume；`:545` 将能解析的通知直接传给状态存储，
没有按用户/内部任务分类的接纳判断。Hook 也只传递哈希身份，不保留任务类别。
所以数据库查询中的 guardian 字符串过滤无法构成整套系统的正确性保证。

### 渲染层丢失 turn 身份

`CodexActivitySnapshot` 只有 sessionHash，`CodexActivityRenderState` 连 session/
turn 身份都不携带。`CodexActivityStateSmoke.swift:1499` 只在 visualState 改变
时处理转换，进度重置也只依赖活动/非活动状态切换。两个任务之间 active→active
切换无法通知渲染器重置；配合进度投影的 max(target,current)，旧任务进度可能
留在新任务上。这是静态确认的输入契约缺口，本轮未对它做屏幕级复现。

### 采集生命周期与资源边界

- 本地增量读取在获取文件大小后使用 `readToEnd()`，随后把旧大小记作 offset。
  同时追加的字节可能下次重复读取；增量批次也没有独立大小上限。
- 本地客户端在 await 回调之后才保存 tail state，缺少运行代次检查。当前常规
  维护循环是串行的，但 stop/start 或测试主动轮询与回调交错时，旧运行的状态
  仍可能写回。CI 曾复现测试主动轮询与后台轮询的重放竞争；去除测试中的双重
  驱动只稳定了测试，并未证明 stop/start 的生产生命周期安全。
- `sessions` 目录存在便声明 connected，不等于发现了可读且可展示的用户任务。
- 有界 event ID 集合存在，但任务、标题、终态和 Token 字典没有统一淘汰策略。
- 对本地文件只检查标准化路径前缀，没有统一验证解析符号链接后的真实文件归属。

以上是静态风险，不能当成截图根因或已完成压力测试的结论。正式修复时应把
实际读取偏移、批次预算、运行代次、缓存寿命和状态健康度纳入验证。

## 保留的正确行为

- 本地解码器已对 `task_complete` 做活动 turn 比对；缺陷在其他入口仍能绕过
  这条约束，不能因此删除已有校验。
- 新版直接 Token 汇总有同 turn 校验、非负整数校验、去重及终态冻结。
- 计划只投影状态计数，运行中封顶 95%；进度动画本身不决定任务终态。
- 收起与等待提醒使用 revision/任务上下文检查；这些保护应保留，但必须绑定
  正确的展示任务。
- 主额度与完成回执的额度来自既有有效快照，不应用内部审核任务 Token 反推额度。

## 一致的修复方向与验证顺序

建议保持现有采集器和渲染效果，通过清晰的职责边界修复，而非同时重写整个 UI：

`采集 → 任务类别与来源证据 → (session, turn) 事件接纳 → 单任务状态 → 展示选择 → 带任务身份的渲染`

1. 定义统一的任务类别和身份契约，所有采集路径执行相同准入规则；内部执行
   单元不可抢占灵动岛。旧环境缺少类别时明确兼容范围，不把未知直接当成强证据。
2. 统一终态、开始、等待、Goal 和回放的接纳规则。先判定身份/来源/有效轮次，
   再修改状态、Token、计划、计时器或当前展示；重复开始幂等。
3. 明确展示选择：当前代码实质上按最近事件切换，并没有读取 Codex 窗口内选中
   任务的可靠身份。应保持“最近活动的用户主任务”这一可实现边界，并保证其他
   任务的终态不会抢占；不要宣称已跟随窗口中的选中任务。
4. 将任务身份带到渲染边界；跨任务重置，同任务连续更新，完成动画只接受明确
   的成功终态，不由 Goal 状态或缺失字段推导。
5. 启动恢复按同一套聚合规则重放或保存足够的累计分段摘要，证明重启前后 Token
   相等；补上读取偏移与运行代次的边界测试。
6. 将上述 9 个诊断场景改成永久回归，再覆盖同一序列的三来源、重复、乱序、
   缺字段、断连重连和跨任务切换组合；运行完整测试和 Universal Release。
7. 用修复后的应用再执行“主任务运行＋真实 guardian 审核”场景，确认主任务
   一直保持运行并在自己的终态完成，最后再做用户视觉确认。

不能通过延后 Stop、固定停在 95%、按 Token 大小猜主任务、隐藏完成动画，或
降低断言来解决这些缺陷。

## 按审计实施的重构

- `CodexActivityTaskIdentity.swift` 建立类别分类、后台元数据查询、任务注册与
  事件接纳规则。SQLite 和 session_meta 均区分用户与内部执行单元；共享通知
  等待 thread 元数据；Hook 在后台查询哈希对应元数据后进入同一状态接纳层。
- `CodexActivityStore` 先接纳身份和来源，再改变计划、Token、Goal 或终态。
  后台终态可更新自身状态，但不能改变当前 snapshot、提醒或收起生命周期。
  同来源拒绝旧时间，跨来源不比较 Hook 送达时间与原生事实时间。
- `CodexActivitySnapshot` / `CodexActivityRenderState` 传递完整任务身份；
  生产进度投影按身份重置，active → active 切换也从新任务自己的进度开始。
- 启动恢复保留所有旧累计分段，通过实时 Token 聚合规则一次批量发布；不再
  截取首末两条。直接汇总仍独占权威，所有原生来源共用严格整数解析。
- 本地读取以实际文件偏移提交，单批最多 1 MiB；跨批超长行整行丢弃。
  状态提交先于 await 回调；本地、共享客户端和 Store 均约束运行代次。
  路径解析符号链接后验证根目录与普通文件；状态与发现缓存具有明确上限。

完整测试 **166 项、0 失败**，包含 9 个原始复现场景及新增跨来源、渲染切换、
停止重启、共享通知准入、超长行、符号链接和批量恢复回归。Universal 与实机
证据、未覆盖边界、签名区别见 [重构验证记录](quotaview-activity-refactor-verification-0.4.6.md)。
