# QuotaView SDD 开发流程

> 文档编号：`QV-SDD-PROCESS-001`
>
> 文档类型：SDD 执行流程（Development Process）
>
> 规格状态：`Accepted`
>
> 生效日期：2026-08-04
>
> 当前生产基线：QuotaView `0.3.5 (Build 5)`
>
> 当前开发入口：全局递增的 `Build 6`；更新规格状态 `Verifying`

## 1. 核心原则

QuotaView 的实现由已确认规格驱动，但规格不能覆盖用户当前明确指令和真实
生产状态。任何功能都必须经过：

```text
事实定位
→ 问题与范围
→ 规格与验收条件
→ 隔离 Prototype（按需）
→ 产品确认
→ 生产实现授权
→ 实现与自动化验证
→ 产品所有者验收
→ 发布与历史归档
```

规格状态、交付状态和发布状态是三个不同概念：规格被接受不代表已实现，
Demo 被确认不代表已进入生产，生产实现完成也不代表已经发布。

## 2. 阶段与出口条件

### 阶段 A：事实定位

输入：用户目标或问题。

必须完成：

- 读取 `AGENTS.md`、版本入口、SDD 索引和相关规格；
- 使用 `git branch --show-current`、`git rev-parse HEAD` 和
  `git status --short --branch` 读取实时开发状态，不依赖 Handoff 中已经
  失效的可变提交哈希；
- 对照生产配置、Release tag 和版本历史，核对生产版本、当前代码、工作区
  修改和已有验证事实；
- 确认本轮读取的 Markdown 已由 Git 跟踪并位于 SDD 注册表或阅读路由中；
  未跟踪草稿、旧 Prototype 和外部参考不参与默认调用链；
- 明确这是修复、规格变更、Prototype、生产实现还是发布任务。

出口：能够用一句话说明生产基线、当前迭代和本轮授权范围。

### 阶段 B：规格化

新增功能或行为变更必须先形成或修改规格，至少包含：

- 稳定文档编号和 Requirement ID；
- 问题、目标与非目标；
- 用户可见行为和状态转换；
- 数据、隐私、辅助功能和兼容性边界；
- 可验证的验收条件；
- 失败与降级行为；
- 变更控制项。

小型缺陷可以更新既有 Requirement 的验收条件，不必为每个像素或拼写创建
新文档；但 PR 必须引用对应规格或明确标记 `Spec impact: None` 并说明理由。

出口：规格进入 `Accepted`，或得到用户允许进行探索性 Prototype。

### 阶段 C：Prototype

只有需要验证技术可行性、交互或视觉方向时使用。Prototype 必须：

- 位于 `Prototypes/` 或系统临时目录，与生产 Target 隔离；
- 在 README 中声明对应规格、交付状态和不得迁入生产的边界；
- 使用虚拟数据时与生产源码隔离；
- 记录测试、Design QA、已确认项和仍未解决项；
- 不修改 Marketing Version、Build、tag 或 Release 历史。

出口：产品方向被拒绝、继续调试，或产品所有者确认并明确授权生产实施。

### 阶段 D：生产实现

只有交付状态已切换为 `Implementing` 后开始。实现必须：

- 按 Requirement ID 拆分代码与测试范围；
- 保持规格中的不变量和禁止回归项；
- 不把 Demo fixture、自动操作或临时 QA 入口带入生产；
- 发现规格缺口时先更新规格，不能用实现细节悄悄改变产品语义；
- 在追踪矩阵中补充生产源码、测试和验证证据。

出口：代码审查、自动化测试和 Release 构建检查完成，状态进入
`Verifying`。

### 阶段 E：验证

验证分为两部分：

1. Codex 执行代码审查、状态逻辑、自动化测试、构建、版本、架构、资源、
   临时入口搜索和 `git diff --check`；
2. 产品所有者运行应用，完成视觉、交互、语言和辅助功能矩阵。

没有产品所有者结论时只能记录“等待用户验收”。Prototype 验收不能替代
生产构建验收。Markdown-only 变更且未触碰源码、资源、配置或构建脚本时，
可按 `AGENTS.md` 跳过 `swift test` 和 Universal Release，但仍必须完成链接、
版本、职责边界、工作区和 `git diff --check` 验证。

出口：所有必要验收完成，或明确记录未通过项并回到规格/实现阶段。

### 阶段 F：发布与归档

只有用户明确授权发布后执行。必须遵守 `AGENTS.md` 的签名、公证、资产、
tag、Release、回下载和双文档联动门禁。

GitHub Release 授权与应用内自动更新序列授权必须分别判断。创建 Stable、
设为 Latest 或上传正式资产，不自动授权发布 appcast；只有产品所有者对精确
版本、Build、tag 和最终 ZIP 明确表示“纳入自动更新序列”后，才允许部署
公开 Feed。未明确批准时默认排除，但可以生成不发布的本地 Fixture 做验证。
一旦获得该明确批准，它同时授权并触发合并、正式签名、公证/Staple、Stable
Release、回下载验证、公开 Feed 与文档联动；除非出现新的凭据、外部状态或
安全阻塞，不得停在合并 `main` 后再次索要发布确认。

出口：

- `VERSION_HISTORY.md` 记录已发生的发布事实；
- `HANDOFF.md` 和 SDD 索引更新生产基线与下一迭代；
- 对应规格交付状态变为 `Released`；
- 追踪矩阵指向最终代码、测试、验收和 Release 证据。
- 如该版本获准进入自动更新序列，Handoff 还必须记录准入原文、精确版本身份
  与最终 appcast 验证结果；未获准版本明确记录为排除状态。

## 3. 对话协议

后续对话中，用户不需要每次复述全部背景。推荐至少说明：

```text
对象：要处理的功能或 Requirement ID
阶段：继续 Demo / 修改规格 / 迁入生产 / 验证 / 发布
目标：本轮希望达到的结果
变更：是否允许改变已冻结的产品方向
```

例如：

```text
继续 MT-UI-002 的 Demo 调试，只修复紧凑态标题遮挡，不改变固定单岛方案，
完成 Prototype 测试后停下，不迁入生产。
```

或：

```text
批准 QV-PRODUCT-ACTIVITY-ISLAND-MULTITASK-001 进入生产实现，先完成
MT-DATA-001 和 MT-SELECT-001，不改版本号、不发布。
```

用户需要特别区分以下用语：

- “继续调试 Demo”不授权修改 `Sources/`；
- “采用这个方案”表示接受规格，不自动授权生产实施；
- “迁入生产”授权修改生产代码，但不自动授权发布；
- “可以发布”才授权进入签名、公证、tag 和 Release 流程；
- “视觉通过”应说明是 Demo 还是生产 App，以及覆盖的外观/语言/辅助功能
  矩阵。

如果用户指令没有明确阶段，Codex 应依据 SDD 索引保持当前阶段，不得自动
扩大权限；只有会实质改变产品方向、从 Prototype 进入生产或触发发布时才
需要用户明确确认。

## 4. PR 与评审门禁

每个 PR 必须提供：

- Spec ID 与 Requirement ID，或 `Spec impact: None` 的理由；
- 规格状态和交付状态；
- 问题、范围与明确非目标；
- 实现前后行为；
- 对应自动化测试；
- 产品验收状态；
- 隐私、辅助功能、本地化和发布影响；
- 临时 Demo/Debug 代码清理结果。

以下情况不得合并为“功能完成”：

- 只有 Demo 证据，没有生产实现；
- 只有编译通过，没有相关行为测试；
- 需要视觉验收但仍未获得用户结论；
- 规格、代码和测试对同一行为的描述不一致；
- 发布文档提前记录尚未发生的 tag、Release 或资产。
